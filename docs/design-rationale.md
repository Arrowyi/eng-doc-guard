# Design Rationale

Why eng-doc-guard works the way it does: the high-level inspirations, the settled decisions they produced, and the methodology it borrowed. Read the matching section before changing a mechanism or paradigm it covers, and rewrite it in place when that mechanism or paradigm changes.

## A lightweight boundary guard, not a process framework

eng-doc-guard audits, proposes, and records; it never makes a project conform to a spec, a phase, or a workflow. Adoption has to stay cheap for teams of any size and style, so the skill is advisory toward documentation a project already maintains: foreign design, architecture, and decision suites get chat suggestions, never edits. The accepted cost is that it cannot enforce documentation discipline the way heavier tooling does — it protects boundaries and records intent, and leaves compliance to the team.

Rejected alternative: spec-driven per-feature process frameworks — not used because they turn a documentation aid into mandatory process every contributor must follow. Revisit only if users consistently ask for enforced gates.

## Deterministic opt-in ownership: only managed documents change

The skill maintains a document only when it created that document or you explicitly enrolled it. Enrollment is a single HTML comment, `<!-- eng-doc-guard:managed -->`, on the first line of the file; a file is managed when that comment opens it (on its first non-empty line, after any frontmatter), and every other file at a governed path is treated as unmarked and left alone. The marker is how a person, a diff, and the agent all agree on ownership without any external bookkeeping — the file carries its own status, and opting out means deleting that line.

Rejected alternative: a repository-root config or ledger file (`.eng-doc-guard.json`) that lists the documents the tool owns. Not used because it pollutes a target repository with a tool-specific dotfile and creates a two-file synchronization hazard — every rename or delete has to update both the document and the ledger. Revisit only if in-file HTML comment markers break a mainstream Markdown toolchain that cannot be handled by leaving those files un-enrolled.

Rejected alternative: implicit path-based takeover, where any document sitting at a conventional path is assumed to be the tool's to rewrite. Not used because assuming ownership of pre-existing, hand-crafted files risks unwanted rewrites and surprise cards on documents the author never asked the tool to touch. Revisit only if users explicitly ask for an opt-out mode aimed at greenfield repositories.

The installer holds the same line mechanically: it touches only the skill roots listed in its manifest and the command files that carry its own managed marker, never a global agent instruction file outside those roots. The accepted cost is that a hand-edited install blocks an upgrade until the user resolves it.

Revisit if clients ship a native package manager that supersedes manifest-tracked installs.

## One reader question per document, two provenance rules

Each governed document answers a single reader question, so a fact lives in exactly one obvious place:

- `README.md` — can an outside user evaluate, install, and invoke this software?
- `AGENTS.md` — which non-obvious facts would a coding agent otherwise get wrong?
- architecture map — what is the macro structure: which units exist, what each owns and does not own, and which way dependencies run?
- design rationale — why do the settled high-level choices, paradigms, and references exist?

The two maintainer-facing documents answer those questions under different provenance rules — different rules about where an allowed fact may come from — and the architecture map is the deliberate exception to the "never record what the code already shows" test. An architecture map exists so a human architect can build a working model of the system without reading every source file, so it is exempt from that test and is synthesized from the code's macro structure. That exemption is separate from pace layering: a coarse directory layout that stops at the major modules the map's prose describes is part of the slow structure — kept when it stands alone, or merged into the module table when it repeats one already in the same file — while per-file "where to look" lookup tables and file-by-file or deep internal trees change at every commit and quickly rot out of date. Recommend one only when multiple decoupled modules or layers interact across non-obvious boundaries and cross-module business or runtime flows; a single-module package, or a simple linear chain a reader can follow from the top-level entry point, does not need one. This is a pace-layering judgment: pace layering is the idea that a system has layers that change at different speeds — the slow, stable structure belongs in the map (system context, module boundaries, dependency directions, cross-module flows, and system invariants), while fast-changing implementation detail belongs to the code. The four documents are also only the top-level entry points this tool maintains, not the only documents a repository may have: standalone topic guides, such as a deployment or CLI reference, stay untouched as link-out targets.

The design rationale is human-originated only: code may confirm that a mechanism exists, but code, the document under audit, and agent-generated artifacts can never supply its motive, inspiration, or reference lineage — only the user's own statement or confirmation counts. This gate is non-circular, because the document cannot vouch for its own reasoning, which is why unconfirmed legacy prose is routed to the user for a confirm-or-drop decision instead of being verified by the agent itself. The accepted cost is that a motive we could plausibly infer stays unrecorded until someone states it.

Revisit if a recurring kind of fact fits none of the four questions.

## Distillation by principle, never by a fixed size

Reasons local to one file or one mechanism belong in a 1–3 line source comment next to the code. The documents keep the high-level layer — boundaries, dependency directions, system invariants, and the reasoning behind them — never per-mechanism detail a reader can recover from the code. Distillation — trimming each document to its essentials — is controlled by principles and by comparison against the document's own purpose, never by a fixed template or a numeric cap: a fixed set of required sections does not fit every repository shape, and any fixed number (a line limit, a source-file count, a minimum number of modules) is wrong for some project and quietly invites deleting valid content just to hit it. Instead, each decision starts from a few heuristic questions scaled to the repo's shape: who reads this document and what single question must it answer, what test must a fact pass to be kept, which content areas genuinely exist here, and where the boundary lines are. As the codebase grows, entries merge or lift to a coarser level instead of multiplying, so a document settles at a size made of essentials; an entry that still earns its place is never dropped for length.

Rejected alternatives: a per-mechanism entry template that forces every mechanism into the same need/approach/cost sentence — not used because it induces code narration and post-hoc motives; and fixed line or entry caps — not used because they reward deletion over distillation. Revisit if a document still bloats while every entry passes its admission test.

## Human-friendly reading, agent-friendly density

Three of the four documents are read by people — outside users of the README, human architects of the architecture map, human designers and maintainers of the design rationale — so each is written in natural, direct prose for that reader, without skill jargon, hollow filler, or telegraphic shorthand. The fourth, `AGENTS.md` / `CLAUDE.md`, is read by a coding agent inside its standing context, so it stays high-density, operational, and exact: commands, co-change rules, and absence invariants. The same fact can therefore read differently across documents by design; each document optimizes for its own reader. A reader of one of the human-facing documents should never have to guess at a project-specific term, so the first time such a term survives distillation it gets a short plain-language explanation — a parenthetical, a one-line example, or an everyday analogy — applied only after the boundary evictions have run, so we gloss only what genuinely earns its place.

## Same-turn convergence cards, marker-aware and fail-closed

The skill stays 100% silent during routine coding, debugging, comment and commit edits, and in-module changes that leave macro boundaries alone. It speaks at exactly two convergence points, and it piggybacks a one-screen numbered Change Card — the single approval surface that lists each proposed change — onto the same reply instead of spending an extra pre-ask turn: when the user explicitly settles a high-level inspiration, methodology reference, or paradigm decision; and when landed code alters the macro boundaries of an existing architecture map (the system-context and container levels of the C4 architecture model), including a coding subagent's diff, which the interactive primary agent evaluates before reporting completion. Both triggers respect ownership: the architecture-map trigger fires only when a managed map exists, so a repository with no map, or only an unmarked one, gets no card and no write from a code change. Consent stays fail-closed — a reply authorizes a card only when that card was the immediately preceding message and the sole pending question, and otherwise the card expires with zero writes and is shown again before anything is written. Subagent and headless runs never emit trigger cards, and an explicit invocation there writes nothing. The accepted cost is one extra round-trip per card, which is the price of never writing a document the user did not approve.

Revisit if users ask for a trusted auto-apply mode for specific change types.

## Key References

- [ARCHITECTURE.md — matklad](https://matklad.github.io/2021/02/06/ARCHITECTURE.md.html) — Record only what is unlikely to change often; boundaries and a coarse structural map beat detailed per-module walkthroughs.
- [Design Rationale Systems: Understanding the Issues — Jintae Lee, IEEE Intelligent Systems 12(3), 1997, DOI 10.1109/64.592267](https://www.computer.org/csdl/magazine/ex/1997/03/x3078/13rRUwhpBHf) — The classic map of design-rationale capture issues; the source of the warning that rationale reconstructed post-hoc from artifacts loses the original reasoning.
- [Integrating different perspectives on design rationale — Shipman & McCall, AI EDAM 11(2), 1997](https://doi.org/10.1017/S089006040000192X) — Rationale emerges incrementally from design communication; we borrowed the distillation of settled communication into structured conclusions and rejected the heavy discussion-record form.
- [Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents? — Gloaguen et al., ETH Zurich & LogicStar.ai, arXiv:2602.11988](https://arxiv.org/abs/2602.11988) — Context files raised inference cost by more than 20% without improving task success, and repository overviews were the unhelpful part; the empirical basis for keeping `AGENTS.md` to non-inferable facts.
- [Best practices for Claude Code — Anthropic](https://www.anthropic.com/engineering/claude-code-best-practices) — The practitioner-side rule that the agent reads the repository itself, so a context file should hold only what is not inferable from it.
- [Documenting Architecture Decisions — Michael Nygard, 2011](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions) — The ADR pattern this skill deliberately contrasts: immutable, append-only records force reconstructing the current answer from a chain of superseded ones.
- [Diátaxis](https://diataxis.fr/) — Documentation forms organized by reader need; the inspiration for one question per document and the opt-in menu.
- [Pace Layering: How Complex Systems Learn and Keep Learning — Stewart Brand, Journal of Design and Science](https://jods.mitpress.mit.edu/pub/issue3-brand) — Systems hold together because their layers change at different speeds: a slow, stable structure constrains a fast, experimental surface. We borrowed the split between the architecture map's slow-changing macro structure and the code's fast-changing detail, and the rule that this boundary is a judgment, not a line count.
- [On the Criteria To Be Used in Decomposing Systems into Modules — D. L. Parnas, Communications of the ACM 15(12), 1972, DOI 10.1145/361598.361623](https://doi.org/10.1145/361598.361623) — Modules should be split around the information each one hides, not around the steps of a process, so a later design change stays local. This is the origin of the information-hiding test that decides what a README leaves out and what an architecture map keeps at the boundary level.
- [The C4 model for visualising software architecture — Simon Brown](https://c4model.com/) — A small set of nested abstractions (system context, containers, components, and code) lets a reader zoom from the whole system to one part without losing the frame. We borrowed its top two levels as the altitude an architecture map stays at, never descending to code.
- [Harness engineering: leveraging Codex in an agent-first world — OpenAI](https://openai.com/index/harness-engineering) — At scale, a short `AGENTS.md` works best as a map that points to deeper sources of truth rather than a long instruction manual. We borrowed that map-not-manual rule and the open `AGENTS.md` convention it describes (https://agents.md/).
- [TDAD: Test-Driven Agentic Development — Reducing Code Regressions in AI Coding Agents via Graph-Based Impact Analysis — Alonso et al., arXiv:2603.17973](https://arxiv.org/abs/2603.17973) — Pointing an agent at the tests a change actually affects cut regressions far more than generic procedure did (6.08% to 1.82% in the paper's evaluation). We borrowed the impact-map idea behind the `Change -> Verification` table in `AGENTS.md`: surface the check a change touches instead of prescribing a ritual.
